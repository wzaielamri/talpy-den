# How it works

```
~/.claude/statusline.sh ──(snippet)──▶ ~/.cache/talpy-den/statusline/<profile>/<session>.json
<profile>/sessions/<pid>.json ─┐
<profile>/jobs/<id>/state.json ┼─▶ package/contents/code/talpy_den.py ──JSON──▶ Plasma, GNOME, VS Code (when a chat changes, else every 2–20 s)
<profile>/projects/**/*.jsonl ─┘
<profile>/sessions/ + ~/.cache/talpy-den/live/ ──▶ live.py --wait (inotify) ──▶ "check now" + each step (live mode)
```

<details>
<summary><b>The details</b></summary>

- **Profiles** are found automatically: every `~/.claude` and `~/.claude-*` folder (what `CLAUDE_CONFIG_DIR` points to). A link such as `~/.claude` → `~/.claude-personal` counts as that profile; everything is keyed by the real folder, so switching the link to another profile never mixes their data. A chat started through the link follows it when it's switched, so it's listed under the profile the link points to now. Profiles logged into the same account (`oauthAccount.accountUuid` in their `.claude.json`) are merged into one section, because they share plan limits. A profile is named by the `.profile-name` file in its folder, else by its folder name (`~/.claude-work`: *work*); `~/.claude` is *main*, and a lone one is named after the account's display name. From `.claude.json` only the account id, plan type and display name are read, plus whether you've trusted a folder (so Talpy Den can tell you before Claude asks) and Claude Code's own cache of your plan usage (`cachedUsageUtilization`); credentials are never touched.
- **Chat state** (a chat is what Claude Code calls a session) comes from Claude Code's own session registry (`sessions/<pid>.json`: `status` `busy` / `shell` / `waiting` / `idle`, with `waitingFor`). Background jobs add their record in `jobs/<id>/state.json`, which also covers jobs whose process has already exited. Dead and reused PIDs are filtered out using the process start time. The rules follow Claude Code's own:
  - Background jobs use the same rules as `claude agents --all`. The live status wins over the job record; a job needs you only when its `tempo` is `blocked` or the chat itself waits.
  - Interactive chats follow Claude Code's terminal status. A dialog you opened yourself (`/model`, `/effort`, …) doesn't count as "needs input", and a background shell still running after the turn counts as working.
- **Plan limits and context** come from the JSON that Claude Code passes to the status line (`rate_limits`, `context_window`), and plan limits also from Claude Code's own cache of them in the profile's `.claude.json` (`cachedUsageUtilization`, what `/usage` fetches), whichever is newer. A status line's numbers are as of its chat's last reply: Claude Code draws an idle chat's status line again an hour after it, when its prompt cache goes cold, with the numbers of then, so a copy counts as of that reply (its `prompt_cache`: `expires_at` less its `ttl`), not of when it was saved. `statusline-snippet.sh` saves a copy of it per chat, under the profile's real folder name. Older copies filed under a link's name only count if they're newer than the link: before it was last switched, that name meant another profile. VS Code's panel runs no status line, and Claude Code updates its cache only when `/usage` runs: so when an account's newest numbers are older than the interval in the settings (*Fetch plan usage older than*: 5 minutes unless you change it; 0 turns it off) while one of its chats works (or ended a turn lately: once more after a turn), the status check has Claude Code fetch them, at most once per interval per account (on SSH hosts too, there), whichever copy of Talpy Den checks (`~/.cache/talpy-den/usage-check.json`): `claude -p /usage --no-session-persistence --setting-sources user --strict-mcp-config --settings '{"disableAllHooks":true}'` (your own settings only, none from the folder it runs in, and no MCP server), started on its own so the check doesn't wait, ended after 60 seconds. It uses no tokens and saves no chat; it runs in `~/.cache/talpy-den/usage-check`, so its chat (there for a second) is never listed, and the empty `projects/<folder>/memory` Claude makes for that folder is removed after it. Never for an account that isn't logged in, and never while nothing of it works.
- **Token totals** are read incrementally from transcripts (at most once a minute, cached per profile in `~/.cache/talpy-den/tokens-*.json`). Lines are de-duplicated per message, and summed per day, so a status check adds up a few numbers instead of every message of the week. Linked folders are followed, so a shared chat's subagents count too.
- **Watching:** `package/contents/code/live.py --wait` (one for all copies of Talpy Den) waits with inotify for a change in each profile's `sessions/` folder, which Claude rewrites whenever a chat's state changes, and in `~/.cache/talpy-den/live/`; then it answers and runs again. A session file that changed makes Talpy Den check at once (a check that's running then runs again once it's done). Steps alone come at most every 0.4 s, and with nothing new it answers every 50 s anyway. What it told Talpy Den last is kept in that folder, so nothing that happens between two runs is missed.
- **Live mode** is `~/.local/share/talpy-den/live-hook.py` (from `live_hook.py`), named in each profile's `settings.json` for Claude's hook events (a prompt, each tool call's start and end, a permission request, a notification, a subagent's start and end, the end of a turn, a chat's start and end) with `async: true`, so Claude doesn't wait for it. It folds each event into the chat's file in `~/.cache/talpy-den/live/` (what it does now, its last 8 steps with the lines an edit added and removed, its running subagents, the first line of what it said last), under a lock, written in one go.
- **What a chat is doing** comes from the end of its transcript: its newest step (a tool call, thinking, writing), your last prompt and Claude's reply since (markdown read as plain text). Its **tasks** are Claude's own task list, `tasks/<session>/<n>.json`. The **files it changed** come from the transcript's `file-history-delta` and `file-history-snapshot` records (each prompt's snapshot is where that turn started), plus its edit tool calls; only what was appended since the last check is read (`~/.cache/talpy-den/chats.json`).
- **Recaps, modes and limits** come from the end of each listed chat's transcript, like what it's doing: Claude's recap is a `system` record of subtype `away_summary` (it counts while no prompt or reply came after it), the permission mode the newest `permission-mode` record (or the one your last prompt carries), and a chat stopped by a usage limit ends with Claude's API error message naming the limit (*You've hit your session limit · resets …*). When that limit resets comes from the account's plan window of that limit (a window that started after the chat stopped means it's over), else from the time in the message.
- **Plans** are the Markdown files a chat in plan mode writes, `<config>/plans/<slug>.md`; the chat's transcript carries its slug (read from its end, kept in `~/.cache/talpy-den/plans.json`), which is how a plan is matched to the chat that made it. Claude's setting `plansDirectory` puts a project's plans in a folder of the project instead (relative to the folder the chat started in, which it must stay inside; Claude takes it from the project's `.claude/settings.local.json`, in a git repository the one in its main folder, else the project's `.claude/settings.json`, else the account's `settings.json`, where it's for every project). Talpy Den reads those settings for each folder chats started in (the first `cwd` of a transcript in each `projects/<folder>`), and for each folder in Claude's own list of projects (`projects` in the account's `.claude.json`, which Claude keeps when it deletes old chats, so a project's plans folder is still read once its chats are gone), and lists the plans of that folder and of the project's `.claude/plans`, each file once (never a plan that's a link, nor a folder that leads out of the project through one: a repo can ship them, to a private key or to `~/.claude`), under the account whose chat made it, else the one with the newest chat there. Two files of one name (a chat that wrote its plan in the account's `plans/`, then, once its project named a plans folder, there) are one plan, the newer file: it's the only line, every action (open, edit, carry out, move, share, the chat's **Plan** tag) takes it, and deleting it takes the older file to the Trash too, so it doesn't come back. What it read is kept in `~/.cache/talpy-den/plan-dirs.json`: a project with a chat in the last hour (or one a plan was just noted or moved to) is looked at at each check, the others every 10 minutes, and a settings file is read again only once it changed, so a check stats about one file per project. The folder of the chat that made a plan is noted the first time they're matched (`~/.cache/talpy-den/plan-projects.json`), so the plan keeps its project once the chat is deleted. A plan file a chat wrote itself, with no slug (a progress log it was asked to keep in `plans/`, say), is matched by the Projects tab to the newest chat that wrote it: the `file_path` of its Write, Edit or MultiEdit call, or what `>`, `>>` or `tee` writes to in its Bash command, by its full path (`~/…`, `$HOME/…` too), in its own transcript or its subagents'. A chat that only reads the file or names it isn't its chat, nor one that shows such a call in a tool's output. It's looked for only for the plans with no chat or project known; each transcript is read once, then only where it grew, at most 512 MB at a time (the rest the next time), and the plan files each one writes are kept in `~/.cache/talpy-den/plan-writes.json` (a few dozen bytes a transcript; an entry goes two days after it was last looked at). **Move to project…** (`jump.py --move-plan`; an SSH host's: `remote.py --move-plan`, `sharing.py` there) links the plan's file into the project's plans folder (a copy on another disk) and removes every account's link to it, never over another file: *keep both* gives it a free name (`<slug>-2`), *replace* moves the other to the Trash first; with *Keep this project's new plans there too* it first adds `"plansDirectory": ".claude/plans"` to the project's `.claude/settings.local.json` (the one Claude reads; its other keys are kept). `--describe` says beforehand where it goes and what to ask, including `git check-ignore` on the new file. **Carry it out** starts a chat with the plan's text (up to 100 KB) as its first message. A shared plan is one file hard-linked into each profile's `plans/` (Claude writes plans in place, so it stays one file).
- **Finding a chat** reads each transcript's name and folder (from its first and last 64 KB, kept in `~/.cache/talpy-den/links.json`) and your prompts from each profile's `history.jsonl`; it runs when you search, not with the checks. The folders it finds are the ones chats ran in; plans are matched by their title and text, memories by their name, description and text.
- **Memories** are Claude's own notes, `<config>/projects/<folder>/memory/*.md` (the name, description and kind at the top of each), listed newest first in their project. The folder a memory is for is found from the `projects/` folder's name, which Claude makes from the folder's path. The account's `CLAUDE.md` is listed under the account, on its own line.
- **Recent chats** are each account's transcripts, newest first, but the ones listed above them (open, or kept for the record), a copy of a listed chat (it starts with the same entry) and a shared chat under the account it was used on last. The status check lists a page more than shows (so **Show N more** shows the next one at once) and counts them all for the title: the next 200 of an account by the same rules (what it read of each is kept in `~/.cache/talpy-den/links.json`), the ones past those by their files, so a check stays as quick with thousands of chats. Past what the check listed, Talpy Den runs the check once more with more of them for that account.
- **Projects** (`week.py --projects`, run when the tab opens and every 10 minutes while it shows): every chat the Recap's cache has whose transcript is still there, by its git repository (else its folder), with the plans (by the folder of the chat that made each, as noted once that chat is gone; one in a project's own plans folder by that project) and memories (by their folder) of every account but the ones you hid, and Claude's last recap from its newest chats. A plan whose project was never known (its chat went before Talpy Den saw it) is listed last, under *Plans whose chat is gone*. What goes on in a project now (its open chats) comes from the status check.
- **Queued tasks** are kept in `~/.local/state/talpy-den/queue.json` (an SSH host's too: they start from here, over ssh). The copy of Talpy Den that notifies starts one once its time has come (`jump.py --start-queued`), which takes it out of the queue first, so of several copies (and the VS Code extension) only one starts it. A chat that goes on by itself is checked first: if its newest turn isn't the limit's message any more, it went on already and nothing happens. A background session that has it open takes that message in where it is, through Claude's background service, the way `claude agents` answers one (its control socket in `/tmp/cc-daemon-<uid>/`, with the key in the Claude folder's `daemon/control.key`; only a service of yours is asked: one at that place run by another user, who made the folder first, is taken for none): the same chat goes on in the same process, with its options and background commands, and a terminal attached to it stays on it. Else (no such session, or the service doesn't take it) the idle Claude that has it open quits (as for **Continue on …**), and once the service no longer holds its session (Claude would start a copy under a new id meanwhile), `claude --bg --resume <chat> "The usage limit has reset: go on where you stopped."` goes on with the same chat in the background (only in a folder Claude trusts, as for background tasks). A background chat's job (`jobs/<id>/state.json`) is woken with the options it saved (`respawnFlags`), so it's given none (Claude would start a copy for any given); the ones it lacks of its permission mode, model and effort are added to them first, while no process has it (from its transcript and status line; those it saved stay): a copy Claude made saves only the options given and the model your settings name, and a later wake uses only those. Should the service still hold the job after 10 seconds (or another chat's job have its short id), Claude starts a copy whatever is given, so the copy is given the job's own. A chat without a job goes on with its transcript's permission mode and its last model and effort. A message from Talpy Chat to a running background chat goes in the same way.
- **Chats that keep going** are kept in `~/.local/state/talpy-den/keep.json`, an SSH host's and a container's too (with their host). The copy of Talpy Den that notifies looks after them at each check (`look_after_kept`): it queues each go-on as one you queue, tries again when one didn't take (nothing new in the chat 5 minutes after it went on) or the turn broke off, and lets the chat go once a turn of it ends by itself. This computer's chats are read from their transcripts. A host's are read from its last answer (`hosts/<host>.json`, below): its status run there is given the chats kept for it (`--kept-chats`), keeps them listed and says how each one's newest turn stands (`keptTurns`); that answer's times are put on this computer's clock, everything is judged as of when it came (an answer from before a go-on never counts as one that didn't take), and one older than 15 minutes isn't used. Their go-ons go on over ssh (a try again with `--force`: whatever its newest turn). A host's go-on or task that couldn't start because the host or the container couldn't be reached (ssh failed, or the container isn't running: not what the host said) is marked so in the queue (`unreachable`) and starts by itself once that host's answer is newer.
- **Chats changing the same files:** two listed chats that each have a process (they can still change files) and changed some of the same files, as Talpy Den reads what a chat changed (Claude's backups and edit tool calls, subagents included; not shell commands).
- **Markdown pages:** without Okular, `package/contents/code/markdown_page.py` turns a plan or run into an HTML page (standard library only: headings, lists, code, tables, quotes, links), written to `~/.cache/talpy-den/agent-runs` and opened in your browser. Everything is escaped, only http(s) links are links, images aren't loaded, and the page's Content-Security-Policy blocks scripts and any loading.
- **Starting a task in the background** runs `claude --bg "<task>"` in the folder, under the account's config folder, in a systemd scope of its own (so the background service it may start outlives a Plasma restart). Commands for background chats (`attach`, `stop`, `--bg`) run without `CLAUDE_CODE_DISABLE_AGENT_VIEW`, which makes Claude refuse them; new chats in a terminal get it, so they open as a normal chat.
- **Stats:** the token scan also keeps per-day sums for 30 days (tokens by model and folder, which chats ran), and counts your prompts per day and folder from `history.jsonl`. A chat's tokens count for the folder it started in. A chat's recap comes from its own transcript and its subagents': prompts, tool calls by name, tokens, and how long Claude worked (each turn, from your prompt to its last step). The price is the status line's `cost.total_cost_usd`: what the chat would cost through the API.
- **Subagents** are read from `projects/<project>/<session>/subagents/agent-*.jsonl` and their `.meta.json`. An agent is done when its transcript ends with its final answer (or the report it hands back), running otherwise, and stopped if its chat ended first. Its task is its transcript's first prompt (a fork's directive); its last steps and report come from the end of the transcript, read again only when it changed (`~/.cache/talpy-den/agent-details.json`). *Open the whole run* reads the transcript in full and writes it to `~/.cache/talpy-den/agent-runs/`.
- **Shared chats** are transcripts with the same file (inode) in several profiles. Each row knows which conversation it shows: a background job that took a chat over counts as that chat while its own transcript holds no messages; a transcript that starts with a shared chat's history is a copy of it. Claude's own rule decides whether a chat moved on (its last `continued-in` record comes after its last finished reply). Where a finished shared chat was used last comes from the status-line snapshots, the prompt history (`history.jsonl`) and, if you use hooks that hold a shared chat to one Claude at a time, their lock file (`~/.local/state/claude-shared-chats/lock-<id>`).
- **Sharing** (`package/contents/code/sharing.py`): hard links the transcript into each profile and the store, moves the chat's `projects/<project>/<id>/` and `file-history/<id>/` folders into the store and symlinks them back. A chat shared the same way by another tool, into a store of its own, is found through its links and handled where it is.
- **Jumping to a chat** (`package/contents/code/jump.py`) finds the window through the chat's process tree. Konsole tabs are switched over Konsole's D-Bus API. A window is raised with a short KWin script loaded over D-Bus, which is how one app can bring another's window to the front on Plasma Wayland. VS Code conversations open through the Claude extension's `vscode://anthropic.claude-code/open?session=…` link. Background jobs are attached under the same config-folder name as the running background service, because Claude keys that service by the folder's *name*. Terminals and VS Code windows Talpy Den opens get a systemd scope of their own (like the apps KDE starts), so restarting Plasma doesn't kill the chats running in them.
- **SSH hosts** (`package/contents/code/remote.py`): `ssh -o BatchMode=yes … <host> python3 -I - --remote`, with `talpy_den.py` on stdin (for sharing, `sharing.py` behind it, `talpy_den.py` loaded as the module it imports); your own text for the host (a reply, a task's prompt, a note) goes on stdin too, in a line before the script, never in the command, which other users of the host see in its process list. Of what a host (or a container) answers, at most 16 MB is read (a real answer has well under 1 MB): one that sends more is stopped, and the host shows "sent too much" until it answers again. In `--remote` mode every row also carries the command that opens it on the host, and the JSON follows a marker line, so login scripts that print a banner can't break it. Connections are shared through `ControlMaster` sockets in `$XDG_RUNTIME_DIR/talpy-den-ssh` (else a folder of yours in `/tmp`): a short path, since a socket's may have at most 107 characters. **Log in…** runs `remote.py --login-here <host>` in a terminal: `ssh -o ControlMaster=auto -o ControlPersist=30m -o ForwardAgent=no -o ForwardX11=no … -T <host> true`, without batch mode, so ssh asks for the password, passphrase, code or host key itself (host keys are checked as always), and the connection it opens becomes the shared one; **Disconnect** is `ssh -O stop`: nothing new uses the connection, and it ends with the last terminal open over it. While it's open, programs running as you can use it, as with a key in your agent.
- **Containers** (`remote.py` too): a container's id is `docker:NAME`, `podman:NAME` or `nerdctl:NAME`, `ENGINE:NAME@HOST` for one on the SSH host `HOST`, and every list keyed by host (the picked ones, stars, hidden ones, the queue) takes it as it is. Its check is `ENGINE exec -i [-u USER] NAME sh -c 'python3 -I - --remote'` with `talpy_den.py` on stdin, as on a host (for one on an SSH host, in an ssh in that host's shared connection). Talpy Den works as the container's own user (its `Config.User`, no `-u`) when that isn't root; only in one that runs as root is USER the `remoteUser` of its dev container (the `devcontainer.metadata` label, the last one wins), or you in a Toolbox or Distrobox (your login name on its host), so a label can only drop root, never give it (a label naming `root` or `0` is ignored). One inspect finds it, kept with the container's id in `~/.local/state/talpy-den/containers.json`, and asked again when the container was made again. A terminal runs `remote.py --attach ID COMMAND`, which checks that the container runs, then becomes `ENGINE exec -it -e TERM -e COLORTERM … sh -c COMMAND` (or `ssh -t HOST ENGINE exec -it …`): jumping to a running chat finds that exec among a terminal tab's processes (VS Code's Dev Containers execs into it by its id). The list (`talpy_den.py --list-containers DAYS`, also run on an SSH host for its own) asks each engine at once, with a timeout each: Podman in one `podman ps -a --format json`, Docker and nerdctl with `ps -a -q` and one `container inspect` of them all; a `docker` that is Podman's script or a link to it (or nerdctl's) is known by its file, asked once per version, and listed once. VS Code opens a container's folder through Dev Containers' `vscode-remote://attached-container+<hex JSON {"containerName": "/NAME"}>` (`@ssh-remote+HOST` for a host's). Since Dev Containers shares your SSH agent and Git credentials with a container it attaches to, a click on a container's VS Code chat with no window attached to it gets `{"ok": false, "ask": "vscode", "message": question}` from `jump.py --remote-vscode` until you say yes once (`--allow-vscode`, kept in `containers.json` with the container's id from a fresh inspect, so one made again asks again); **Open in a terminal instead** runs the chat's `terminalCommand` (its `claude --resume` there) through `remote.py --attach`. An SSH host's VS Code chat with no window connected to the host asks the same way once per host (VS Code's server there can read your clipboard and open links here), the yes kept by the host's name in `containers.json`, and its **Open in a terminal instead** opens over `ssh -t`.
- **Each host's last answer** is kept in `~/.cache/talpy-den/hosts/<host>.json` (only your user can read it) with how far the host's clock was from this one's: at start it shows at once (`remote.py --last`), dimmed, until the first check answers.

</details>
